# 标准业务需求开发范式

本文档用于规范后续在当前 RuoYi-Vue3 分离版项目中新增业务模块时的分析、设计、编码、验证和交付方式。

适用场景：

- 新增一个业务菜单。
- 新增一个业务数据表。
- 新增列表、新增、修改、删除、详情、导出等常规管理功能。
- 页面中存在从其他主数据表引用数据的字段。
- 引用字段需要保存快照，并在主数据变化后提示业务数据存在差异。

典型示例：

```text
刀具管理
└── 零件刀具清单
```

其中“零件刀具清单”引用“刀具数据库”中的刀具信息，保存时记录刀具快照；当刀具数据库发生变化时，清单行置灰并显示“刀具信息变化”。

## 1. 需求输入标准

提出同类需求时，建议按以下结构描述：

```text
在【父级目录】下新增【菜单名称】。

功能目标：
用于管理【业务对象】。

字段包括：
【字段1】、【字段2】、【字段3】……

操作能力：
支持列表查询、新增、修改、删除、批量删除、导出。

引用关系：
【字段A】、【字段B】来源于【被引用模块/表】，不支持手工录入。
点击【引用】图标后弹出查找窗口，选择已有数据后带回字段。

数据变化规则：
引用数据保存快照。
如果被引用数据后续发生变化，业务列表中对应数据置灰，状态显示【变化提示文案】。
```

如果有更多业务约束，应补充：

- 是否需要唯一性校验。
- 是否需要状态启停。
- 是否需要逻辑删除。
- 是否需要导入。
- 是否需要字典项。
- 是否需要按部门或用户做数据权限。
- 是否需要审批、流程、打印、附件或图片上传。

## 2. 开发前确认清单

进入编码前，必须先确认以下事项：

| 确认项 | 说明 |
| --- | --- |
| 菜单层级 | 新菜单挂在哪个目录下，是目录、菜单还是按钮 |
| 页面名称 | 浏览器左侧显示的菜单名称 |
| 路由路径 | 前端动态路由 `path` |
| 组件路径 | 前端页面 `component`，必须匹配真实 Vue 文件 |
| 权限标识 | 后端、菜单按钮、前端按钮保持一致 |
| 主表字段 | 当前业务对象自身字段 |
| 引用字段 | 来源于其他模块，不允许手工录入的字段 |
| 快照字段 | 引用时需要保存的字段副本 |
| 变化判断字段 | 用哪些字段对比主数据和快照 |
| 导出范围 | 导出当前查询结果还是选中记录 |
| 验证方式 | 需要覆盖哪些接口和页面行为 |

菜单层级示例：

```text
刀具管理
├── 刀具数据库
│   └── 机加刀具信息
└── 零件刀具清单
```

## 3. 命名规范

后端命名建议：

```text
业务对象英文名：PartToolList
数据库表名：tool_part_tool_list
权限前缀：tooling:partToolList
Controller：PartToolListController
Domain：PartToolList
Mapper：PartToolListMapper
Service：IPartToolListService
ServiceImpl：PartToolListServiceImpl
Mapper XML：PartToolListMapper.xml
```

前端命名建议：

```text

页面文件：frontend/src/views/{module}/{business}/index.vue
接口方法：listXxx、getXxx、addXxx、updateXxx、delXxx
```

```text
{module}:{business}:list
{module}:{business}:query
{module}:{business}:add
{module}:{business}:edit
{module}:{business}:remove
{module}:{business}:export
```

示例：

```text

tooling:partToolList:edit
tooling:partToolList:remove
tooling:partToolList:export
```

## 4. 数据库设计范式

业务表建议包含三类字段：

### 4.1 主业务字段

当前业务对象自身的数据，例如：

```text
part_no             零件号
part_name           零件名称
production_unit     生产机组
process_no          工序号
process_name        工序名称
tool_life           刀具寿命
tool_life_unit      寿命单位
status              状态
```

### 4.2 引用关系字段

用于记录引用数据的主键，不直接展示给普通用户编辑：

```text
tool_id             引用的刀具主键
```

### 4.3 引用快照字段

用于保存选择引用对象时的字段副本：

```text
material_code       刀具物料编码快照
tool_name           刀具名称快照
tool_brand          刀具牌号快照
tool_spec           刀具规格快照
tool_model          刀具型号快照
tool_category       刀具类别快照
manufacturer        生产厂家快照
```

快照字段的目的：

- 保留业务发生时选择的引用信息。
- 避免主数据后续变化导致历史业务数据被静默覆盖。
- 支持和当前主数据对比，提示用户引用信息已变化。

### 4.4 审计字段

沿用 RuoYi 常规字段：

```text
create_by
create_time
update_by
update_time
remark
```

## 5. 引用数据处理范式

引用类字段必须遵循以下规则：

1. 前端不允许用户手工录入引用字段。
2. 前端通过“引用”图标打开查找弹窗。
3. 用户在弹窗中选择一条主数据。
4. 前端将引用主键和展示字段带回表单。
5. 保存时，后端只信任引用主键。
6. 后端根据引用主键重新查询主数据。
7. 后端将主数据字段写入快照字段。
8. 如果引用主键不存在，后端拒绝保存。

关键原则：

```text
前端负责选择体验，后端负责数据可信。
```

也就是说，即使前端传入了 `materialCode`、`toolName` 等字段，后端也不能直接保存这些文本，而应根据 `toolId` 重新读取主数据并覆盖快照。

## 6. 主数据变化提示范式

当业务表保存引用快照后，列表查询时需要同时读取当前主数据，并进行差异判断。

差异判断建议包括：

- 引用主数据已被删除。
- 引用主数据物料编码变化。
- 引用主数据名称变化。
- 引用主数据牌号、规格、型号、类别、厂家等关键字段变化。

后端列表结果建议返回：

```text
toolInfoChanged     是否变化，0 否，1 是
displayStatus       展示状态，例如：正常、停用、刀具信息变化
```

前端展示规则：

- `toolInfoChanged = 0`：正常展示。
- `toolInfoChanged = 1`：整行置灰。
- 状态列显示变化提示文案，例如“刀具信息变化”。
- 允许用户查看原快照字段。
- 如需同步最新主数据，应通过明确的“重新引用”或“更新引用”动作完成，不做静默覆盖。

## 7. 后端实现范式

新增普通业务模块时，按以下文件结构实现：

```text
backend/ruoyi-admin/src/main/java/com/ruoyi/web/controller/{module}/XxxController.java
backend/ruoyi-system/src/main/java/com/ruoyi/system/domain/Xxx.java
backend/ruoyi-system/src/main/java/com/ruoyi/system/mapper/XxxMapper.java
backend/ruoyi-system/src/main/java/com/ruoyi/system/service/IXxxService.java
backend/ruoyi-system/src/main/java/com/ruoyi/system/service/impl/XxxServiceImpl.java
backend/ruoyi-system/src/main/resources/mapper/{module}/XxxMapper.xml
backend/sql/{table_name}.sql
```

Controller 要求：

- 继承 `BaseController`。
- 列表接口使用 `startPage()` 和 `getDataTable(list)`。
- 详情、新增、修改、删除、导出接口齐全。
- 增删改导出加 `@Log`。
- 接口加 `@PreAuthorize`。
- 导出使用 `ExcelUtil`。

Service 要求：

- 新增和修改时统一填充引用快照。
- 引用主键为空时抛出业务异常。
- 引用数据不存在时抛出业务异常。
- 不在 Controller 中写引用快照逻辑。

Mapper XML 要求：

- 列表查询左连接引用主表。
- 返回变化标识字段。
- 查询条件覆盖主要业务字段和引用快照字段。
- SQL 字段和 Java 属性映射清晰，不依赖模糊自动映射。

## 8. 前端实现范式

新增普通业务页面时，按以下文件结构实现：

```text
frontend/src/api/{module}/{business}.js
frontend/src/views/{module}/{business}/index.vue
```

页面能力必须包含：

- 查询表单。
- 数据表格。
- 分页。
- 新增弹窗。
- 修改弹窗。
- 删除确认。
- 批量删除。
- 导出按钮。
- 权限按钮 `v-hasPermi`。

引用字段 UI 要求：

- 引用字段输入框设置为只读或禁用手工录入。
- 输入框后方增加“引用”图标按钮。
- 点击后打开查找弹窗。
- 查找弹窗支持按关键字段查询。
- 弹窗表格支持单选。
- 选择后回填引用主键和快照展示字段。

变化提示 UI 要求：

- 接收后端 `toolInfoChanged` 或同类字段。
- 变化数据整行置灰。
- 状态列显示后端返回的 `displayStatus`。
- 不在前端自行猜测是否变化，变化判断以后端为准。

### 8.1 刀具管理类 UI 标准

刀具管理类、物料数据库类页面默认沿用当前“机加刀具信息”页面的 UI 风格，具体标准见：

```text
docs/机加刀具信息UI开发范式.md
```

默认执行口径：

- 顶部页签采用 Edge 风格连体页签。
- 查询区首行只保留核心查询条件，详细条件进入弹出面板。
- 搜索、重置按钮固定在查询区右侧。
- 表格支持点击行选中，并同步顶部按钮启用状态。
- 物料状态与流程状态使用不同配色体系。
- 权限决定按钮是否显示，业务状态决定按钮是否可用。

## 9. SQL 与菜单范式

每个新增业务模块应配套一份独立 SQL 文件，包含：

- 创建业务表。
- 新增菜单。
- 新增按钮权限。
- 给本地默认角色授权。

菜单 SQL 必须确认：

```text
menu_name       菜单名称
parent_id       父菜单 ID
order_num       排序
path            路由路径
component       组件路径
route_name      路由名称
menu_type       M 菜单 / C 目录 / F 按钮
perms           权限标识
icon            图标
visible         是否显示
status          是否正常
```

注意事项：

- 菜单 `component` 必须能对应前端真实文件。
- 按钮权限必须和后端 `@PreAuthorize`、前端 `v-hasPermi` 一致。
- SQL 文件必须使用 UTF-8。
- 导入 SQL 时使用 `utf8mb4`，避免中文乱码。

导入示例：

```bash
docker exec -i ruoyi-mysql mysql --default-character-set=utf8mb4 -uroot -proot123456 ry-vue < backend/sql/{table_name}.sql
```

## 10. 验证范式

同类需求完成后，至少执行以下验证：

### 10.1 构建验证

```bash
./scripts/build-backend.sh
./scripts/build-frontend.sh
```

### 10.2 服务验证

```bash
./scripts/status-dev.sh
```

确认：

- MySQL healthy。
- Redis healthy。
- Backend running。
- Frontend running。

### 10.3 接口验证

必须覆盖：

- 登录成功。
- `/getRouters` 返回新增菜单。
- 列表接口正常。
- 新增接口正常。
- 详情接口正常。
- 修改接口正常。
- 删除接口正常。
- 导出接口正常。
- 权限标识有效。

引用类需求还必须额外验证：

- 不选择引用数据时不能保存。
- 选择引用数据后可以保存。
- 手工伪造的引用文本不会被保存。
- 后端保存的是根据引用主键查询出的快照。
- 修改主数据后，业务列表返回变化标识。
- 前端变化行置灰，并显示变化提示文案。

### 10.4 浏览器验证

必须人工确认：

- 左侧菜单显示正确。
- 面包屑、标签页、页面标题正常。
- 查询表单可用。
- 新增、修改弹窗可用。
- 引用弹窗可打开、查询、选择。
- 只读引用字段不能手工编辑。
- 表格字段展示完整。
- 导出按钮可用。
- 变化数据置灰效果符合预期。

## 11. 交付说明范式

完成后，交付说明应包含：

```text
1. 完成了哪些菜单和页面。
2. 完成了哪些后端接口。
3. 新增了哪些数据库表和菜单权限。
4. 引用字段和快照规则如何实现。
5. 主数据变化时如何提示。
6. 已执行哪些构建和接口验证。
7. 当前访问地址。
8. 如菜单未出现，提示退出重新登录或刷新动态路由。
```

交付说明中应列出关键文件路径，便于后续维护。

## 12. 标准执行流程

后续同类需求统一按以下流程执行：

```text
1. 需求澄清
   确认菜单层级、字段、引用关系、快照规则、变化提示规则。

2. 设计落表
   设计业务表、引用主键、快照字段、审计字段、状态字段。

3. 后端实现
   创建 Domain、Mapper、XML、Service、Controller、导出注解和权限。

4. 前端实现
   创建 API、页面、表格、表单、引用弹窗、状态展示和权限按钮。

5. SQL 导入
   创建业务表、菜单、按钮权限，并授予默认角色。

6. 构建重启
   后端构建、前端构建、必要时重启服务。

7. 自动验证
   验证登录、菜单、CRUD、导出、引用快照、变化提示。

8. 人工确认
   浏览器检查菜单、页面交互和视觉状态。

9. 文档记录
   更新需求、环境、验证或模块说明文档。
```

## 13. 禁止事项

后续同类需求中禁止：

- 让用户手工输入本应来自主数据的引用字段。
- 只在前端限制输入，不在后端校验引用数据。
- 保存前端传来的引用文本作为可信数据。
- 主数据变化后静默覆盖历史业务快照。
- 只做页面不做权限。
- 只做接口不做菜单。
- 只做 CRUD 不做导出，但需求中写了导出。
- 修改菜单 SQL 后不验证 `/getRouters`。
- 导入中文 SQL 时不指定 `utf8mb4`。
- 新增业务模块后不跑后端和前端构建。

## 14. 后续扩展方向

当同类需求变复杂时，可在此范式基础上扩展：

- 引用数据同步按钮。
- 快照差异详情弹窗。
- 历史版本记录。
- 批量重新引用。
- 导入模板。
- 字典化状态和类别。
- 数据权限隔离。
- 操作审计增强。
- 附件、图片、工艺文件关联。
