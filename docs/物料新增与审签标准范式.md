# 物料新增与审签标准范式

本文档基于当前“刀具管理 -> 刀具数据库 -> 机加刀具信息”模块的最新实现整理，目标是把“新增物料、提交流程、状态流转、权限控制、前后端约束”固化为后续可复用的标准范式。

适用范围：

- 机加刀具类物料主数据。
- 后续其他“物料数据库类”业务模块。
- 需要“提交 -> 校对 -> 审核 -> 生效”的审签流程型业务。

## 1. 当前标准对象

当前基准对象为：

- 菜单：`刀具管理 -> 刀具数据库 -> 机加刀具信息`
- 业务对象：`MachiningTool`
- 表：`tool_machining_tool`
- 权限前缀：`tooling:machiningTool`
- 流程定义 Key：`machining_tool_approval`
- 流程业务类型：`machining_tool`

当前对象的核心字段包括：

- `toolId`
- `materialCode`
- `toolName`
- `toolBrand`
- `toolSpec`
- `toolModel`
- `toolCategory`
- `manufacturer`
- `status`
- `materialVersion`
- `materialStatus`
- `approvalStatus`
- `changeApplyBy`
- `processInstanceId`
- `processDefinitionKey`
- `createBy/createTime/updateBy/updateTime/remark`

其中：

- `materialCode` 必须唯一。
- `materialVersion` 为系统维护字段，新建固定为 `A01`，不可手工修改。
- `materialStatus` 只表示物料状态。
- `approvalStatus` 只表示流程状态。
- `changeApplyBy` 记录当前变更申请人，仅在变更链路中使用。

## 2. 状态模型

### 2.1 当前数据库中保存的流程状态

字段：`approvalStatus`

可选值如下：

| 值 | 流程状态文案 |
| --- | --- |
| `draft` | 待提交 |
| `processing` | 审批流 |
| `rejected` | 驳回 |
| `effective` | 审签完成 |
| `change_processing` | 变更审批中 |
| `changing` | 变更中 |
| `change_rejected` | 变更驳回 |

### 2.2 当前数据库中保存的物料状态

字段：`materialStatus`

可选值如下：

| 值 | 物料状态文案 |
| --- | --- |
| `draft` | 草稿 |
| `processing` | 审签中 |
| `effective` | 生效 |

### 2.3 当前业务规则

当前实际生效的规则如下：

- 新增物料后，`materialVersion` 强制写成 `A01`，`materialStatus` 和 `approvalStatus` 都强制写成 `draft`。
- 已生效物料不得通过普通修改接口直接修改。
- 普通申请人只有在 `materialStatus = draft` 时才能修改物料。
- 普通申请人只有在 `materialStatus = draft` 时才能删除物料。
- 普通申请人只有在 `approvalStatus in (draft, rejected)` 时才能提交或重新提交。
- `tool_auditor` 可修改非生效物料，可代为提交；删除和强制删除能力按权限保持不变。
- 已生效物料如需修改，具备 `tooling:machiningTool:edit` 的用户应先发起修改申请审签。
- 修改申请审批通过后，物料进入 `approvalStatus = changing`，仅 `changeApplyBy` 对应的变更申请人可编辑并提交原始审签。

## 3. 新增物料标准操作

### 3.1 入口权限

新增按钮权限：

- `tooling:machiningTool:add`

只有用户具备该权限时，前端显示“新增”按钮；后端接口也必须同时校验该权限。

### 3.2 标准新增流程

标准新增物料操作如下：

1. 用户打开“机加刀具信息”列表页。
2. 点击“新增”按钮。
3. 填写物料属性。
4. 前端提交 `POST /tooling/machiningTool`。
5. 后端校验物料编码唯一性。
6. 后端写入 `createBy`。
7. 后端强制设置 `materialVersion = A01`、`materialStatus = draft`、`approvalStatus = draft`。
8. 保存成功后，前端提示“新增成功，物料已保存为草稿”。

### 3.3 新增阶段的标准要求

- 新建物料默认不是“审批流”状态。
- 新建物料默认不是“生效”状态。
- 新建物料默认版本为 `A01`。
- 新建完成后必须先形成草稿，再由用户主动提交审签。
- 物料主数据录入和流程启动必须拆成两个动作，不允许“保存即发起流程”。

## 4. 物料修改、删除、提交标准

### 4.1 修改标准

修改权限码：

- `tooling:machiningTool:edit`

标准规则：

- 普通用户必须同时满足“有修改权限 + 是申请人本人 + `materialStatus = draft`”才可修改。
- `tool_auditor` 可修改非生效物料。
- `materialStatus = effective` 时，所有角色都不能通过普通修改接口直接编辑。
- `approvalStatus = changing` 或“变更后原始审签驳回”时，仅 `changeApplyBy` 对应用户可编辑。
- 普通修改接口必须保留原 `materialVersion`，不得接受前端传入版本覆盖。
- 后端服务层必须再次校验，不能只依赖前端按钮显隐。

### 4.2 删除标准

删除权限码：

- `tooling:machiningTool:remove`

当前规则：

- 普通用户必须同时满足“有删除权限 + 是申请人本人 + `materialStatus = draft`”才可删除。
- `tool_auditor` 走删除时，后端会直接按强制删除逻辑处理。
- 如果物料存在运行中的流程实例，审核角色删除时会先终止流程，再删业务数据。

### 4.3 强制删除标准

强制删除权限码：

- `tooling:machiningTool:forceRemove`

当前规则：

- 只有用户具备该权限时，前端才显示“强制删除”按钮。
- 强制删除无视物料状态。
- 如果流程仍在运行，必须先终止流程实例，再删除物料。

### 4.4 提交审签标准

提交权限码：

- `tooling:machiningTool:submit`

当前规则：

- 普通用户必须是物料申请人本人，才可提交当前物料。
- `tool_auditor` 可代为提交。
- 当前允许提交的流程状态为：`draft`、`rejected`。
- 变更中的物料提交原始审签时，仅 `changeApplyBy` 可提交。
- 提交成功后，`approvalStatus` 更新为 `processing`。

## 5. 审签流程标准

### 5.1 流程定义

当前机加刀具原始审批流程定义为：

```text
提交 -> 校对 -> 审核 -> 业务生效 -> 结束
```

修改申请审批流程定义为：

```text
提交修改申请 -> 校对 -> 审核 -> 变更放行 -> 结束
```

对应节点角色：

- 校对节点：`tool_checker`
- 审核节点：`tool_auditor`

### 5.2 流程状态流转

标准流转如下：

```text
物料状态：新增保存 -> draft
物料状态：提交审签 -> processing
物料状态：校对/审核驳回 -> draft
物料状态：审核通过 -> effective

流程状态：新增保存 -> draft
流程状态：提交审签 -> processing
流程状态：校对/审核驳回 -> rejected
流程状态：审核通过 -> effective
```

### 5.3 回调更新标准

流程回调只负责更新以下几类字段：

- `materialStatus`
- `approvalStatus`
- `materialVersion`
- `changeApplyBy`
- `processInstanceId`
- `processDefinitionKey`
- `updateBy`

回调标准如下：

| 场景 | materialStatus | approvalStatus |
| --- | --- | --- |
| 启动流程 | `processing` | `processing` |
| 审签通过 | `effective` | `effective` |
| 审签驳回 | `draft` | `rejected` |

变更审批状态机如下：

| 场景 | materialStatus | approvalStatus | changeApplyBy | 版本 |
| --- | --- | --- | --- | --- |
| 发起修改申请 | `effective` | `change_processing` | 当前发起人 | 不变 |
| 修改申请通过 | `draft` | `changing` | 保留发起人 | 不变 |
| 修改申请驳回 | `effective` | `change_rejected` | 清空 | 不变 |
| 变更编辑后提交原始审签 | `processing` | `processing` | 保留发起人 | 不变 |
| 变更后原始审签通过 | `effective` | `effective` | 清空 | 递增 |
| 变更后原始审签驳回 | `draft` | `rejected` | 保留发起人 | 不变 |

版本与快照规则：

- 当前版本字段为 `materialVersion`，格式为 `A` + 两位数字，范围 `A01` 到 `A99`。
- 首次原始审批通过时写入 `A01` 完整字段快照。
- 修改申请审批通过、变更编辑保存期间不递增版本，也不写新快照。
- 变更后原始审批最终通过时，版本从当前值递增一位，并写入新版本完整快照。
- 超过 `A99` 时，后端拒绝继续递增。
- 快照落表到 `tool_machining_tool_version`，唯一约束为 `(tool_id, material_version)`。

## 6. 权限与角色配置标准

### 6.1 机加刀具权限清单

| 权限码 | 含义 |
| --- | --- |
| `tooling:machiningTool:list` | 列表菜单访问 |
| `tooling:machiningTool:query` | 查询 |
| `tooling:machiningTool:add` | 新增 |
| `tooling:machiningTool:edit` | 修改 |
| `tooling:machiningTool:remove` | 删除 |
| `tooling:machiningTool:export` | 导出 |
| `tooling:machiningTool:submit` | 提交审签 |
| `tooling:machiningTool:forceRemove` | 强制删除 |

修改申请复用 `tooling:machiningTool:edit`，历史版本查看复用 `tooling:machiningTool:query`。

### 6.2 当前角色授权结果

当前数据库中的授权结果如下：

| 角色 | 角色标识 | 当前已授权能力 |
| --- | --- | --- |
| 刀具管理员 | `tool_manager` | 列表、查询、新增、修改、导出、提交 |
| 刀具管理-校对 | `tool_checker` | 列表、查询、导出 |
| 刀具管理-审核 | `tool_auditor` | 列表、查询、新增、修改、删除、导出、提交、强制删除 |

### 6.3 权限控制标准

权限控制必须分三层：

1. 菜单/按钮层：决定是否显示入口。
2. 控制器层：通过 `@PreAuthorize` 控制接口访问。
3. 服务层：通过“申请人判断 + 状态判断 + 角色判断”控制业务合法性。

必须遵守：

- 前端隐藏按钮不能替代后端校验。
- 后端 `@PreAuthorize` 不能替代服务层业务校验。
- 涉及状态流转时，必须在服务层校验“当前状态是否允许当前操作”。

## 7. 前端实现标准

前端页面必须同时体现以下规则：

- 列表页同时展示“物料状态”和“流程状态”。
- 顶部批量按钮和行内按钮都要做同一套业务判断。
- 强制删除按钮只能在具备 `tooling:machiningTool:forceRemove` 时显示。
- 行内按钮显隐不仅取决于权限，还取决于当前用户是否为申请人、当前状态是否允许。

当前机加刀具页面的实现原则如下：

- `canEdit`：已生效且允许发起变更时，打开修改申请弹窗；变更中仅 `changeApplyBy` 可编辑；普通草稿由申请人编辑；审核角色可编辑非生效、非变更审批中的物料。
- `canDelete`：申请人本人且 `materialStatus = draft`，或审核角色。
- `canSubmit`：申请人本人且 `approvalStatus in (draft, rejected)`，或审核角色；变更中的物料仅 `changeApplyBy` 可提交。

UI 风格、查询区、页签栏、状态标签配色、表格行选择等前端交互标准见：

```text
docs/机加刀具信息UI开发范式.md
```

## 8. 后端实现标准

后端建议固定分为三层职责：

### 8.1 Controller 层

职责：

- 接收请求。
- 做权限注解控制。
- 做参数接收和基础校验。
- 调用 Service。
- 在提交流程时构造 `WfStartProcessRequest`。

### 8.2 Service 层

职责：

- 唯一性校验。
- 申请人校验。
- 变更申请人校验。
- 状态合法性校验。
- 审核角色越权能力处理。
- 版本字段保护。
- 删除前业务检查。

### 8.3 Workflow 回调层

职责：

- 流程启动时把业务状态置为 `processing`。
- 审签通过时把业务状态置为 `effective`。
- 审签驳回时把业务状态置为 `rejected`。
- 修改申请启动、通过、驳回时维护 `change_processing`、`changing`、`change_rejected`。
- 原始审批通过时维护版本递增和历史快照写入。
- 不在流程回调中处理页面权限逻辑。

## 9. 推荐的标准范式

后续如果再做新的“物料数据库”类模块，建议直接复用以下范式。

### 9.1 数据表标准字段

除业务字段外，必须至少包含：

- `material_status`
- `approval_status`
- `material_version`
- `change_apply_by`
- `process_instance_id`
- `process_definition_key`
- `create_by/create_time`
- `update_by/update_time`
- `remark`

### 9.2 标准权限集

建议固定生成以下按钮权限：

```text
{module}:{business}:list
{module}:{business}:query
{module}:{business}:add
{module}:{business}:edit
{module}:{business}:remove
{module}:{business}:export
{module}:{business}:submit
```

如存在审核越权删除场景，再额外增加：

```text
{module}:{business}:forceRemove
```

### 9.3 标准流程集

建议默认按以下流程建模：

```text
待提交 -> 审批流 -> 审签完成
         \-> 驳回
生效 -> 变更审批中 -> 变更中 -> 审批流 -> 审签完成
        \-> 变更驳回
```

节点分工建议固定为：

- 申请人提交
- `tool_checker` 校对
- `tool_auditor` 审核

### 9.4 标准业务规则

推荐固定以下口径：

- 新增只生成草稿。
- 新增版本固定为 `A01`。
- 保存不自动提交流程。
- 普通申请人只能操作自己的物料。
- 普通申请人修改必须受物料状态约束。
- 已生效物料不能直接编辑，必须先走修改申请审批。
- 变更完成后重新提交原始审批并通过时，版本递增并写入历史快照。
- 审核角色可越过普通草稿限制处理非生效物料。
- 强制类操作必须独立权限，不得与普通删除共用一个权限码。

## 10. 当前实现说明

当前实现已经将“物料状态”和“流程状态”拆成两个独立字段：

- `material_status`
- `approval_status`

当前定义如下：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `material_status` | `draft` | 草稿 |
| `material_status` | `processing` | 审签中 |
| `material_status` | `effective` | 生效 |
| `approval_status` | `draft` | 待提交 |
| `approval_status` | `processing` | 审批流 |
| `approval_status` | `rejected` | 驳回 |
| `approval_status` | `effective` | 审签完成 |
| `approval_status` | `change_processing` | 变更审批中 |
| `approval_status` | `changing` | 变更中 |
| `approval_status` | `change_rejected` | 变更驳回 |

## 11. 拆分后的收益

- 展示语义更清晰。
- 权限判断可以明确区分 `material_status`、`approval_status` 和 `change_apply_by`。
- 流程驳回不再与“草稿可修改”产生歧义。
- 版本递增和历史快照由流程回调统一维护，避免前端手工改版本。
- 后续业务模块更容易复用统一规则。

## 12. 开发落地检查清单

后续新增同类模块时，建议按以下顺序验收：

1. 新增保存后是否强制为草稿且版本为 `A01`。
2. 物料编码是否唯一。
3. 普通申请人是否只能修改自己的草稿物料。
4. 审核角色是否只能修改非生效物料。
5. 普通申请人是否只能删除允许删除的状态。
6. 提交后是否进入 `processing`。
7. 驳回后是否进入 `rejected`。
8. 通过后是否进入 `effective`。
9. 已生效物料是否只能发起修改申请，不能直接编辑。
10. 修改申请通过后是否仅 `changeApplyBy` 可编辑并提交原始审签。
11. 变更后原始审签通过时版本是否递增并写入历史快照。
12. 强制删除是否仅在具备权限时显示按钮。
13. 强制删除审批流中的数据时，是否先终止流程实例。

## 13. 结论

当前“机加刀具信息”模块已经形成了一套可复用的基础范式：

- 新增先落草稿。
- 版本由系统维护，历史版本以快照表保存。
- 流程独立提交。
- 普通申请人受申请人身份和状态约束。
- 已生效修改走独立变更审批，变更编辑只开放给变更申请人。
- 审核角色拥有非生效数据的越权处理能力。
- 前端按钮显隐与后端接口校验双重生效。
- 流程状态通过统一回调更新。

后续新物料模块应优先沿用该范式，并默认按“物料状态/流程状态双字段”建模。
